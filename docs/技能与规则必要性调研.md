# 技能与规则必要性调研

日期：2026-10-10。阶段：调研结论，尚非实施方案；未新增技能或改变正式v0.6.0。

## 判断依据

用户明确：自动化用例编写与维护最重复费时；常见质量问题是用例遗漏或预期缺少依据；服务全体测试人员。用户认为功能缺陷可直接描述提交、老化异常直接分析即可，defect-analysis暂不实施。

判断是否需要技能，看是否有反复发生的任务、稳定输入输出、跨人员统一收益及能观察的验收结果。只有专业知识或会分析问题，不足以成为封装理由。规则保存跨任务不变的底线；技能组织特定任务流程；项目资料提供接口事实。这三者不能互相替代。

## 现有能力与实际不足

已实现testcase-iteration和pytest-generation。前者完成夹爪266条写法验收；后者已有Fixtures、Allure、单接口及恢复保护要求，但本次资料不足以证明真实项目完整生成/维护已验收。缺陷分析、覆盖审查、测试报告仍无可调用技能。

现有interface-contract、case-change、generation-review模板已经覆盖依据与映射字段，不应再新增同义模板；不足在真实任务是否填写、是否有变更前后证据及可用的项目示例。52项知识库静态检查验证文件与镜像，不证明断言正确、业务覆盖完整或恢复有效。

Tuya历史覆盖记录区分executable与gated_skeleton，说明“映射有一行”不等于自动化可执行。其历史交接还记录重编号导致趋势断裂、资料缺失和占位参数阻断。上述为历史记录证据，不是对当前Tuya分支新做的自动化审计。

## 需求排序：现有技能优先，新增技能克制

### 高优先：完善pytest-generation，不另建同义技能

应补充维护场景，而非只描述生成：接口新增、参数变化、返回结构变化、异常类型变化、Sheet改名及既有断言修正。输出应明确哪些文件/用例受影响、保留哪些、改什么及依据；不把所有文件都重生成。

增加经真实项目验证的只读查询、setter回读恢复、异常和状态转换例子，明确Fixtures/数据读取/Allure的本地差异。项目路径及连接值不能直接复制到公共示例。优先验证一个只读接口的生成副本与人工审查，再评估扩展。

语法检查之外检查可观察行为：是否只断言“没报错”、是否比较真正业务返回、setter是否保存原值且恢复失败能暴露、是否遗漏等待与超时。无法静态证明的结论保留人工评审，不设计关键词命中就宣称合格的检查器。

### 高优先：完善testcase-iteration的需求变更与遗漏审查

增加可操作的“需求/接口→测试点→现有用例”对照，输出缺失、重复、不适用及依据不足。已有功能不再单独建立用例评审技能。将新增/修改/删除落实到具体受影响用例，来源记在附件，不破坏原Excel字段。没有完整批准清单时不报告覆盖率。

预期依据分层：批准需求/协议说明正确行为；SDK源码核实当前实现及可调用入口；历史测试结果说明发生过什么。不能把实现返回值自动当成正确预期。未知值具体到返回、错误码、单位或阈值，不写泛泛“待确认”。

### 中优先候选：coverage-review，是否独立需真实任务验证

这是目前最有理由考虑的新技能：团队经常需要在已有用例和自动化之间找遗漏，它有明确交付——映射和缺口清单。若仅在写用例时顺便检查，留在testcase-iteration即可；若经常独立审查发布范围和跨模块自动化进度，才单独封装。

必须分开四种状态：已有测试设计；已有自动化映射；实现了可执行且有业务断言的代码；有当前版本执行证据。另列骨架、跳过、缺依据、未执行，不把skip算通过或把骨架算可执行。名称匹配只是候选关联，不代表语义覆盖；多个参数行不增加接口分母。

### 暂缓：test-report

只有团队频繁交付固定格式报告、反复整理真实结果时才封装。已有Word模板与简单对话能解决的报告，不必新增技能。若未来实现，核心应是真实结果聚合、同版本去重、缺失/未执行/跳过/恢复失败区分，而不是“写一份漂亮报告”。

### 暂不需要

缺陷分析与老化日志分析：按用户工作方式直接对话处理。Git安装更新：现有脚本与说明已承担，不必再包装一个技能。新人接入：先完善项目接入模板。运动、固件升级、ROS连接：属于项目专用规则和另行授权任务，不推成跨产品公共技能。

## 规则需要完善什么

1. 任务边界规则已具备，保留。用例编写、自动化生成/维护、静态自检、collection、执行不得相互默认授权；不再增加一套审批流程。
2. 预期依据规则已有原则，需落实为使用既有interface-contract记录项目/版本/位置/已核实事实/缺口，并为冲突区分流程选择与接口事实确认。无需把来源哈希塞进每个业务单元格。
3. 版本变更规则需补可执行细节：变更前基线、受影响接口和用例、稳定ID、历史结果保留、新版本未执行状态；不能因接口或Sheet改名直接破坏趋势。
4. 覆盖状态规则需补统一定义：设计、映射、可执行、已执行分别报告；骨架和缺依据不隐藏。是否实现独立技能不影响这个规则的价值。
5. 项目适配规则已有差异索引，但需核验当前分支、资料版本及实际样例。SDK与ROS不共享运行契约；通用规则不带设备地址、固定成功码或运动参数。
6. 技能验收规则需补团队可重复的真实请求与合格输出示例。结构检查不是行为验收；新规则通过一个项目还需至少另一个不同结构项目验证适用边界。
7. 共享规则需精简漂移：维护源、镜像和安装副本已有明确关系，但README仍夹杂旧阶段现状，ROADMAP仍默认推动缺陷分析。后续应纠正现状入口，保留历史交接而非让每一段历史都充当现行规则。

## 接下来应由用户决定的事项

三个问题已经收敛，正式实施前按用户AGENTS要求仍需“确认执行”。建议先选择完善pytest-generation与用例遗漏/依据审查；coverage-review保留候选，test-report暂缓，defect-analysis暂停。此处仅是调研排序，不授权修改项目自动化或发布新版。
