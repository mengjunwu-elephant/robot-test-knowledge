# 迁移目的、方案对照与来源空项（PIT-006）

## 场景与实际表现

2026-10-20 至 2026-10-21，ultraArm P1 旧用例按固件模板迁移，并审查一份已生成后又被改过的屏幕 v1.2.9 工作簿。

- 主控 v1.0.8 副本把原表「测试类型/方法/维度」写入「测试目的」，例如等价类划分法、正交实验法、错误推断法。用户指出后，测试方法被去掉，三张功能表的测试目的改成该行要验证的结果。原文件当时正打开，修订写在另一个文件。
- 屏幕 v1.2.9 审查发现序号中的屏幕计时、Blockly 循环、RAM 掉电，以及同一条预期和备注互相矛盾，这些和已确认范围不一致。审查报告了差异，没有改原件。
- 主控副本和屏幕全量表的结构检查未通过。缺的优先级、步骤或编号在来源里本来就是空的，副本按原文留空，没有补写。

## 证据边界与原因

依据是该次对话记录和 2026-10-23 用户对三条处理的确认：测试目的改写成「验证…」；内容差异只报告；来源空项单独写成「来源既有缺口、不补」。本次没有重新打开那些工作簿，不能断言文件现在仍是对话里的状态。当时技能已要求测试目的说明验证目标，并要求不猜填；可确认的是迁移时把测试方法填进了测试目的，结构结论没有把来源空项和生成缺陷分开。

## 正确做法与适用范围

迁移旧表时，测试方法不进入测试目的和备注。测试目的按该行预期写成「验证…」。步骤、预期和优先级按已确认原文保留。预期为空或对不上时写待确认。用户当次明确要求测试目的按原文时，以该句为准。

已有确认方案或交接范围时，对照该范围报告差异，并继续核对范围内的需求/协议依据、遗漏测试点、步骤与预期对应及可执行性；与方案一致不代表内容正确。不因审查改写工作簿。来源单元格本来为空、且已确认按原文迁移保留的优先级、步骤或编号，单独列为「来源既有缺口、不补」。来源有值而副本丢失，仍按生成缺陷报告；不因来源空项把整本说成生成失败。归因与质量结论分开：来源既有缺口仍须报告对必填完整性及可执行性的影响，不能据此宣称结构通过；未确认保留的空项，按当前任务范围和可信依据补齐，或列具体待确认，不猜填。不把 ultraArm 的表名、环境或条数当成其他项目的模板。
