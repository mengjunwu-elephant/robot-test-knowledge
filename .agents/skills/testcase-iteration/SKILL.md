# 用例编写、迭代与审查

先读取[团队公共规则](references/team-rules.md)。本技能随v0.8.4分发。记录安装清单版本及来源：包内build-info.json的渠道、提交和内容指纹；仓库来源记录Git提交与未提交状态。客户端无法给出提交时记录未知及当前SKILL文件哈希，不只凭版本号判定内容。旧对话不会因仓库更新自动升级。读取目标项目资料后，按任务选择以下流程。

按当前任务查看[经验入口](references/pitfalls/index.md)，只读匹配短记录，不加载全部历史或扩大授权。

## 1. 读取项目与可信资料

核对当前规则、已有用例、需求/协议、软件/固件/SDK完整版本及必要源码，按[项目差异](references/project-context.md)识别差异并重新核验快照。先明确行为、可观察结果、预期依据和恢复责任；不从当前实现反推正确答案。

## 2. 审查已有用例

读取[完整审查交付](references/review-completion.md)。默认结构、格式、内容和视觉四项；用户明确缩小范围时遵守其选择。

- 已授权范围直接做只读检查，不套用生成副本的三道关口，不自动审查pytest或执行测试。
- 格式按团队基线与批准项目差异检查。夹爪是实例，产品名和Sheet名不是触发条件。
- 使用review_workbook.py检查结构及填写规则，review_format.py --baseline team检查直接样式；跨项目字段/复杂表头按[批准布局](references/field-layout.md)适配，特殊标准用项目配方；检查实际列覆盖，明确排除项只报告部分范围。
- 内容依据、视觉抽样及无法检查的项分别报告。已有确认方案或交接范围时，内容对照该范围只报告差异，不因审查改写工作簿。漏项直接补齐，未完成不称完整审查。

## 3. 编写或迭代用例

读取[确认流程](references/confirmation-flow.md)：确认实际Sheet范围→独立测试点评审→确认完整方案→生成副本。新方案至少收敛版本变化、模板/Sheet范围、预期依据及交付边界三类问题，取得“确认执行”。已有相同范围授权不重复确认。

测试点评审以接口名称、对应测试点、待确认依据为核心，按Sheet/协议分组。非接口场景用功能/测量项目；主视图不放评审编号，原ID/行号留追溯附件，不改Excel字段。存在多个测试环境或运行模式时，对每个测试点明确操作对象、可观察对象、预期动作、禁止副作用和通过条件；例如纯仿真与真机联动必须说明模型和真机各自是否应动作。环境列是否需要分组按已确认的模板和执行记录需求决定，不因场景不同就重复建列，也不把不同判据含混合并。

按项目类型读取具体写法：

- [通用软件](references/general-software.md)。
- [固件、协议或Python库](references/firmware.md)。
- [ROS Service、Topic、Action](references/ros.md)。
- [资料冲突](references/conflicts.md)：提示具体差异，保留接口事实缺口。

## 4. 写法与格式

先读[可直接操作写法](references/practical-writing.md)和[通用格式](references/cell-format.md)。

- 前置写必要状态；每步真实接口/参数或人工动作；预期逐编号对应。参数、单位、限位、返回和异常须有依据。
- 旧表「测试类型/方法/维度」不写入测试目的或备注。测试目的按该行预期写成「验证…」；预期为空或与步骤对不上时标待确认。步骤、预期和优先级仍按已确认原文。用户当次明确要求测试目的按原文时，遵守该句。
- 同接口连续相同公共字段按规则合并，不跨独立步骤/预期/结果，不机械追加验证行凑数量。
- 正常、边界、异常、状态、超时、恢复与回归按真实契约选取，不要求所有接口凑齐维度。
- 团队正文微软雅黑10号、垂直居中、换行和全边框；编号/功能/接口/优先级居中，描述及结果按配方左对齐。表头与封面分开，冲突先提示选择。
- 新表复制assets/templates的适用模板；旧表保留字段与结构，示例结果不能当真实记录。
- 复制模板后按批准范围填写，不重建或简化未获准修改的Sheet。交付前对照原模板核对首页/环境Sheet的字段、位置、合并区、样式和登记区；删除、改名或重排Sheet须有明确范围依据。

## 5. 副本、验证与交付

按[字段与检查](references/workbook-review.md)制作逐行变更清单，保留原Sheet/ID、公式、历史失败和回归。来源、版本及选择记录在附件，不擅自加列。SDK title与ROS automation_id分开，写用例不重构Fixtures、Allure或恢复逻辑。

在最终交付文件上完成结构、格式、内容和视觉检查。来源单元格本来为空的优先级、步骤或编号，单独标「来源既有缺口、不补」；来源有值而副本丢失仍算生成缺陷，不因来源空项把整本说成生成失败。交付前逐组核对相邻相同公共字段的合并范围、合并外框，以及独立步骤、预期和执行栏未被合并。生成后任何会影响单元格、Sheet或版式的修订，都要对最终文件重跑受影响的检查并重新查看受影响区域，记录检查方法、Sheet/区域与结果；编号、状态和非空统计不能替代合并或视觉检查。模板要求保真的Sheet须与模板核对结构及样式。工具是只读静态检查，不替代语义、视觉和设备验收。格式工具不适配或失败时完成已知部分，明确未知字段及未验证项。按[示例](references/examples.md)核对表达，不能复制演示预期至真实项目。

交付文件/Sheet/改动、依据、冲突、检查结果和未执行事项；不同环境分别记录，未执行不填Pass，旧结果不冒充新版本。新方案同步总文档，任务结束更新唯一交接并评估规则技能。
