# 自动化生成/维护交付复核

按照确认用例与实际项目逐项阅读修改副本，不靠数量、关键字或AST通过判定正确。

- 数据字段、分类及稳定身份和原表对应；请求字段未混入验证/恢复控制字段。
- 每个测试点有真实业务观察和断言，expected无依据就待确认；不是仅字段存在、success状态或pass。
- SDK返回解包/异常、ROS响应/Topic指标采用正确场景契约，未抄跨项目值。
- setter原状态完整、恢复调用及回读可见，恢复失败不吞掉，多状态不漏恢复。
- Fixture、参数化、marker/skip、中文Allure及脱敏参数证据符合项目规则。
- 等待有超时，占位/缺资料显式阻断，不把门控骨架称成熟业务测试。
- 堵转按两次弹窗夹住制造堵转的调用，确认堵转后再调用测试接口。进行中场景先核验进入状态调用的返回语义和状态时机，再按[场景参考](in-progress-and-stall.md)生成：仅在返回时已处于目标状态且仍有效时立即测试；需要状态确认则采用批准的有界观察方式。阻塞到动作结束、契约不明或无批准实现时保留待确认，不生成伪“进行中”调用顺序。进入状态的命令和参数来自本条批准前置，不统一后移等待。
- 改动清单说明受影响用例、保留内容、来源及恢复责任；只执行当前授权验证。

交付“静态已验证、人工已评审、业务待执行、依据待确认”分别说明。例子与源码是输入证据，规则目标和现有实现不一致时提示缺口，不擅自重构原项目。
